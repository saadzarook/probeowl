ProbeOwl follows a record across your SQL Server, Oracle and MariaDB databases and your REST APIs, in Dev, UAT or Production. It checks that a flow did what it should and shows you the one place it didn't. Anyone on the team can run a check with one identifier, without writing SQL. How it works

Describe a record once. Check it with one identifier, forever.

The engineer who knows a system writes a short YAML file: where a record lives, how its keys lead from one system to the next, and what should be true. After that, anyone on the team can check any record of that kind, in any environment, from a web page.

  1. Enter any identifier

    A top-up ID, a payment reference, a card number, an email. ProbeOwl finds the subject it belongs to, or lists the matches if there are several.

  2. Follow the key graph

    From the first record to every related one, across databases and APIs, including fan-out to many rows, such as every card on an account.

  3. Check the expectations

    Amounts match, the ledger balances, exactly one card is active. Each check passes, fails, or is skipped with the reason.

  4. Read the evidence

    One outcome per location, the masked rows behind it, and an audit entry. Then compare with a healthy record or open the team's runbook.

Outcomes

“Not there” and “couldn’t look” are never the same answer.

Most debugging mistakes start with a query that returned nothing for the wrong reason. ProbeOwl keeps eight outcomes apart, so a failed read can never pass for a missing record.

following the keys…
Found

The record is there, with its rows as evidence.

Missing

ProbeOwl looked, and there is no such record.

Waiting

Not there yet, within the time the flow is allowed to take. Defined, not yet reported in v0.1.

Stale

The replica is too far behind to trust a Missing.

Blocked

A key it needed was empty, so it couldn’t look.

Ambiguous

More records than expected, or an identifier that matched several subjects. Pick one.

Error

The read itself failed. The reason names no host or login.

Not configured

A connector has no binding in this environment. In v0.1, the run is refused before it starts.

Missing data never passes a check. If the ledger isn’t there, “credits equal debits” is skipped, not passed as 0 = 0. And when a Production replica’s lag can’t be read, every Missing says so: replica lag unknown, the record may not have arrived yet.

Beyond one record

Compare with a healthy record

ProbeOwl finds a recent record of the same kind that passed, runs the same probe on it, and shows only the fields that differ. Fields that always vary, like amounts and timestamps, stay out of the way.

A shared knowledge base

The team’s queries, steps and runbooks in one searchable place, linked to the problems they solve. When a run fails, the right runbook appears next to it with the values filled in. Reviewed reads run in one click; write queries are only ever copied, with a header naming the environment and run.

Compare files

Two configs, exports or API responses, compared by structure in JSON, YAML, CSV, XML and more. Secrets stay masked, and nothing leaves your machine.

A kill switch

One command stops every read, globally, for one application or for one connector, before any password is opened. It’s recorded with who and why.

Every environment

The same probe runs against Dev, UAT, Staging or Production, each with its own connection settings. QA can verify a flow in UAT before release; Production adds replicas, a required reason and reference, and a red banner so nobody mixes them up.

No SQL needed

Pick the application and the check, paste an identifier, and read the result. People new to a system can investigate safely on day one, and learn how it fits together from the key graph and the knowledge base.

Safe by design

Read-only is enforced in code, not left to good intentions.

To change data on a system it probes, several independent safety layers would each have to fail at once. Every one of them is covered by tests, run against real SQL Server, Oracle and MariaDB servers.

One SELECT onlyEach query is parsed and must be a single SELECT. Links to other databases, hints, temporary tables, locks and comments a database would execute are refused. Values are always bound, never pasted into SQL.
What was reviewed runsThe SQL runs exactly as written. ProbeOwl only adds parameter markers, a row cap and, on SQL Server, OPTION (MAXDOP 1), and the evidence shows the exact text that ran.
No locks, no loadNo lock waits on SQL Server, at most one second on MariaDB (Oracle readers never block), a statement timeout, serial plans, and a hard row ceiling per connector that no probe can raise. Plans are read to catch full scans before a probe is saved.
Replicas in ProductionProduction always reads a replica. Lag above the threshold pauses the connector; unknown lag puts a caveat on every Missing.
Masked personal dataPersonal data is masked before results leave the runner, in the API, the logs and every export.
Everything auditedWho ran it, the identifier, the systems read and the masked results. In Production, a reason and a reference are required. The audit is append-only.
Nothing exposedThe server listens on 127.0.0.1 only, checks every request’s Host, and checks the origin of every request that changes something. Passwords live in your system keychain, never in a file, and TLS is verified unless a binding opts out with a stated reason.
Honest about timeA time keeps its exact instant on every database. A comparison that would silently shift by hours is refused until the query converts it.

Who it’s for

One tool for the whole team.

read-only, always

Developers

Is it my code or the data?

  • Debug a ticket by pasting its identifier.
  • Prove a fix with the same probe before and after a release.
  • Probes are YAML in git, checked in review by owl check.

Quality engineers

Did the flow really finish?

  • Check every downstream system, not just the screen.
  • Verify a flow in Dev or UAT before release, with no SQL to write.
  • Attach evidence to a defect, not screenshots.

Support and new joiners

What should I check, and how?

  • Run a team-made check with one identifier.
  • Follow the knowledge base step by step.
  • Learn how systems connect from the key graph.

Security

Who looked at Production, and why?

  • Fewer people with direct database access.
  • Least-privilege, read-only logins, proven by tests.
  • Every lookup attributable, with personal data masked.

Get started

Running in four commands.

ProbeOwl runs on your machine. owl init asks a few questions, writes a config folder and saves the password to your system keychain. Then open the web app and import your schema.

Want to look around first? The guide shows how to run the built-in examples against local test databases.

Read the guide →

  1. Install the owl command
    uv tool install probeowl
  2. Put it on your PATH, once, then open a new terminal
    uv tool update-shell
  3. Describe your first application and database
    owl init
  4. Start ProbeOwl, then open http://127.0.0.1:7878
    owl serve --config probeowl
