# v0.2: where ProbeOwl is going next

This note outlines v0.2: what it holds, in what order, and the rules each part keeps. It is an
outline, not a specification. Each part gets its exact API, inputs and outputs in its own reviewed
PR before it is built. What ProbeOwl does and why is in [design.md](design.md); the roadmap is in
[implementation-plan.md](implementation-plan.md).

## Scope and order

v0.2 is the first release of **No YAML required**: a person goes from `owl serve` to a working
probe without opening a file or a terminal. That work ships in four phases, one per release
(see the roadmap). v0.2 is phase (a), and phase (a) is what defines v0.2.

| Order | Part | Release |
| --- | --- | --- |
| 1 | The baseline measurement ([#27](https://github.com/saadzarook/probeowl/issues/27)), before any v0.2 code | — |
| 2 | Phase (a): first-run setup in the browser, Add connection, and credentials on this machine | v0.2 |
| 3 | Global search: a command palette | v0.2 if ready, else v0.2.1 |
| 4 | The MCP server for drafting, `owl mcp` | v0.2 if ready, else v0.2.1 |

A part that is not ready moves to v0.2.1; it does not hold up phase (a). v0.2 goes out after the
same checks as v0.1: the wheel check, the native runs on each affected database, and the
maintainer's newcomer retest on the release wheel.

## Measured

The newcomer path, from install to a first Validate on the card example, is measured three ways:

- a scripted run on the v0.1 wheel before phase (a) ([#27](https://github.com/saadzarook/probeowl/issues/27)),
  counting every CLI answer, browser action and character typed, with machine time per segment,
  and run again after each phase;
- the maintainer's own timed run;
- one outside person's first run, after phase (c).

**The baseline**, on the v0.1.0 wheel ([results](../dev/measure/results/v0.1.0.md)): 61 actions and
366 characters typed, install to first Validate on the card example.

**The target for v0.2**: at most 30 actions and 120 characters on the same path, measured the
same way (`dev/measure/newcomer_baseline.sh`) after phase (a).

**Phase (a) alone does not reach it.** An estimate of the path after phase (a), counting each
step as the baseline does:

| Step | Baseline | After phase (a) | What changes |
| --- | ---: | ---: | --- |
| Commands typed | 5 / 92 | 3 / 53 | `uv tool install probeowl`, `uv tool update-shell`, `owl serve`; no `owl init` |
| Setup: application | 21 / 167 (`owl init`) | 6 / 24 | name, owning team, untick Dev and Production, Create, confirm |
| Setup: connection | (in `owl init`) | 8 / 71 | MariaDB, database, login, password, TLS and its reason, Test, Save |
| Import and confirm the labels | 7 / 0 | 2 / 0 | confirmed where the import lists them |
| Open the web app | 1 / 0 | 1 / 0 | |
| New entity | 11 / 15 | 11 / 15 | unchanged until phase (b) |
| New Validate probe | 12 / 82 | 12 / 82 | unchanged until phase (c) |
| First Validate | 4 / 10 | 4 / 10 | |
| **Total** (actions / characters) | **61 / 366** | **about 47 / 255** | |

What still costs the most after phase (a):

1. **Writing the probe's first check**: 12 actions and 82 characters, 52 of them the expectation
   typed by hand. Phase (c)'s blocks and probe by example replace the typing with choices.
2. **The two install commands**: 44 characters that no screen can remove.
3. **The connection's fields**: 71 characters, 40 of them the reason for trusting a self-signed
   certificate. Against a server whose certificate verifies, that reason isn't asked.
4. **The entity wizard**: 11 actions. Phase (b)'s graph starts from the imported tables.

The probe, the entity and the Validate alone take 27 actions and 107 characters, so reaching 30
and 120 needs phases (b) and (c) as well. v0.2 is measured against the target after phase (a), and
the gap is reported with each phase until it is closed.

## Phase (a): first run and Add connection

When `owl serve` finds no applications, the browser opens a setup screen instead of an empty app.
`owl init` stays, for scripts. Every screen writes the same YAML files through the same write rules
as today (preview as a diff, hash check, audit), and every lookup still goes through the same guards.

**First-run setup.** Three short steps: the application, its environments, its first connection.
The application id follows the name, with environment words stripped. Dev, UAT and Production are
suggested; Production is marked red and is the only one that asks about a replica. Nothing is
written until Create.

**Add connection.** Also reached from Connectors, for a new connector or a missing environment.

- **Type tiles**: SQL Server, Oracle, MariaDB and REST API, one click each.
- **Paste a connection string**: a JDBC, ODBC or URL string is parsed in the browser into host,
  port, database and login. The string itself is never sent or stored. A password inside it moves
  to the password field.
- **Test connection on an unsaved draft**: the same fixed reasons as today's Test connection
  ("authentication failed", "the host did not answer"), each with what to check. It never echoes
  the server's own text.
- **The Production replica question**: a Production SQL binding must read from a replica, as
  `owl check` already requires.
- **TLS and its reason**: verify the certificate (the default), trust this server's certificate, or
  no TLS. Trusting asks why, written to the binding as `trust_server_certificate_reason`, which
  `owl check` already requires in Production.
- **The password goes straight to the keychain** (see below).
- **Then the schema import**: a passing test offers the import and lists the tables it found, with
  their suggested table labels and links, confirmable on the spot.

**Credentials on this machine.** One write-only secret endpoint takes every password: a new
binding, the missing-password prompt and Change password.

- It answers 204 with no body. No GET exists. The password is never logged, never in an error,
  never in an audit record: the audit records only that it changed.
- It passes the same 127.0.0.1, origin and header checks as every other write.
- **Missing password**: a teammate whose keychain lacks a binding's password (say, the config came
  from git) sees *This connection needs your password for UAT* on Connectors, with a field right
  there. A run that needs it stops before any lookup with the same prompt. Saved, it is tested at
  once.
- **Change password**: an action on each binding, followed straight away by Test connection.
- **One keychain name per binding**: `keyring:probeowl/<connector>.<env>`, as today, with no
  migration. Two applications can have connectors with the same id, so both `owl connector add`
  and the Add connection form warn when a password already exists under that name, and ask before
  overwriting it.
- **The audit commits with the keychain write.** The audit event is written in a transaction that
  commits last. If the audit fails, the keychain entry is put back as it was and the save is
  refused, as file saves and `owl connector add` already do.
- **A test proves it never leaks**: it runs every path that takes a password (save, change,
  missing-password prompt, test connection, a refused request) with a known test password, then
  scans the request log, `owl serve`'s log, every response body, the audit records and traces for
  it.

**Setup without a store.** Today `owl init` and `owl connector add` carry on without a store, with
a warning that the change is not audited. Phase (a) revisits this: the browser setup creates the
default store first, so its writes are audited from the first one. The CLI's behaviour is decided
in phase (a)'s contract PR.

**Contract changes.** Proposed in one `contract` PR, with its code and regenerated web client,
before phase (a) is built:

- create an application (preview, then write; only for a name not loaded yet);
- create a connector or add a binding (the binding's secret is always a `keyring:` reference);
- the write-only secret endpoint;
- connector status says whether this machine has a password for each binding (never its value);
- Test connection on an unsaved draft binding.

## Later phases: decided

Phases (b) to (d) ship in v0.3 to v0.5. These decisions are final and recorded here so the
public design is complete:

- **Blocks are custom React components, not Blockly.** Each block is one expectation, drawn as a
  sentence with real selects and inputs. What blocks can't express stays an editable code block.
- **No drag at first.** Blocks move with up and down buttons and <kbd>Alt</kbd>+arrows. Drag is
  revisited after the maintainer's retest.
- **Time windows.** `within(a, b, 5m)` means at most 5 minutes apart, in either order. Order is its
  own check, `a before b`. "Within 5 minutes after" is two checks.
- **Probe by example** takes 2 or 3 records known to be healthy. Only checks that hold for all of
  them are pre-ticked, and each shows which samples it held for. Ranges and "same across systems"
  are preferred to exact values. It suggests identifier patterns from the samples' values. PII
  columns are never proposed.
- **Plain-English sentences get singular and plural right**: "At most 1 card is active", "At most
  2 cards are active", with tests for 0, 1 and 2, each location kind, and negation.

## Global search

A command palette, opened with <kbd>Ctrl</kbd>+<kbd>K</kbd> or <kbd>/</kbd>.

**What it finds**: applications, entities, probes, locations, connectors, runbooks, imported tables
and columns (with their table labels), guide pages (reusing the bundled guide's search index), and
runs, by run id or by the subject identifier as stored.

**What it does**: New entity, New probe, Add connection, Reload configuration, and Inspect or
Validate with the value typed.

**What it never does**: search inside run data, or unmask anything. A masked subject matches only
its stored, masked form. A test searches for a known email and finds no masked run.

Keyboard first, results grouped by kind, recent items at the top, scoped to the current application
with an "all applications" toggle, and axe-clean.

## MCP server: drafting with an AI assistant

`owl mcp` runs a Model Context Protocol server over stdio. It opens no network port.

**The assistant drafts, the person pastes.** The server never writes anything, never returns a
credential, and every host or URL it emits is a placeholder. The person pastes the draft into the
file and reloads the configuration themselves.

This is narrower than the agent access parked in [design.md](design.md#ai-agent-access-mcp--parked):
it reads no probed database, starts no run and reads no run data. That design stays parked.

**Tools** (outline; exact inputs and outputs are proposed for review before building):

| Tool | What it returns |
| --- | --- |
| `drafting_guide(kind)` | How to write an entity, probe, connector, catalog or runbook: required fields, rules (time filter, identifiers, cardinality, PII, the expression language), common mistakes, and where the file goes |
| `template(kind)` | A skeleton with placeholders only: `<host>`, `<port>`, `<database>`, `<read-only login>`, `<base URL>`, `secret: keyring:probeowl/<connector>.<env>` |
| `examples(kind)` | The bundled example entities, probes and runbooks |
| `check_draft(kind, text, application?)` | The same findings as `owl check` and the save checks (plan checks only if a connection is available), plus "paste this into `<path>`, then Reload configuration". Writes nothing |
| `list_config(application?)` | Applications, entities, probes, locations, connectors (id, type, environments bound) and runbooks. No hosts, URLs, ports, logins, secrets or keyring names |
| `schema(application, connector, environment)` | Imported table and column names, types, keys, table labels and links. Never rows or values |

**Credential safety.**

- `check_draft` scans each draft for passwords, tokens, connection strings with credentials,
  private keys and real hostnames or IP addresses. It never echoes them back (they are shown
  masked) and replies: remove this; passwords go in the keychain through Add connection or
  `owl connector add`, and hosts stay in the connector file you write yourself.
- No tool can read the keychain, the store's secrets, run data or evidence.
- A test sends a draft containing a known test password and a real host through every tool, and
  checks that neither value appears in any output or log.
- Every call is audited as "via MCP" with the tool's name, without the draft's text.

**Guide page.** *Draft with an AI assistant*: connecting Claude Desktop, Claude Code and VS Code; an
example conversation from request to pasted file; and the rule that the person pastes and reloads.

**Out of scope**, for future issues: an assistant writing files, starting runs, or reading data.
